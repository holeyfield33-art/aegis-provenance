## #39 — sensitive-tool / egress-contract mismatch (confirmed exploitable)

**This was not theoretical.** Before the fix:

```ts
decideAttribution(
  'send_widgets',
  { to: 'alice@corp.example', bcc: 'attacker@evil.example' },
  {},
  [
    wrapSpan({ origin: 'system', content: 'assistant' }),
    wrapSpan({ origin: 'user-session', content: 'Email the report to alice@corp.example.' }),
    wrapSpan({ origin: 'tool-result', content: 'note' })
  ]
)
```

returned `{ verdict: 'allow', ... }`. `send_widgets` matches the sensitivity
table's `/^send_/` name pattern (sensitive, `requiresUserSession: true`), but
isn't one of the exact aliases in `tool-contracts.ts`'s `TOOL_ALIASES`, so
`resolveCanonicalTool` returned `null` and `egressContract` returned `'none'`.
`egressAuthorizationCheck` cannot distinguish "unclassified name" from "a
recognized tool that legitimately has no email/host destination" — both
return `'not-applicable'` — so the call fell back to the generic gates. Those
evaluate `hasUserSessionIntent` once for the **whole call**: the authorized
`alice@corp.example` recipient appeared verbatim in the user's own message,
satisfying intent for the entire call including the unauthorized `bcc`
sibling field, which itself matched no span at all (an unmatched value
contributes nothing to `anyValueInertOnly`). Net effect: the exact
authorized-recipient-plus-hidden-BCC smuggle the structural egress-
authorization module (`egress.ts`) was built to close in a prior audit round,
reopened by tool-naming choice alone.

**Fix:** `decideAttribution` now checks `resolveCanonicalTool(actionName)`
first, for every sensitive action, and blocks immediately — before
evaluating destinations or the generic gates — when it resolves to nothing.
Per the issue's explicit instruction ("do not merely add
`send_customer_email` to `TOOL_ALIASES`"), the fix is the general invariant,
not a name patch: verified with a property-style test sweeping seven
unrelated unregistered names across every sensitivity-table pattern
(`send_*`, `delete_*`, `transfer_*`, `*permission*`), each checked both with
a destination-free payload (to prove the block is name-driven, not
destination-driven) and the BCC-smuggle shape. Canonical, deliberately
non-egress tools (`delete_file`, `transfer_funds`, `set_permission`,
`search`, `read_file`) are unaffected — confirmed with an explicit regression
that they still resolve and still rely on the generic gates exactly as
before.

## #40 — canary detection normalization weakness

`canaryDetection` normalized with a local `normalizeText` (whitespace
collapse + lowercase) instead of the `normalizeMatchText` the provenance-
matching pipeline uses (invisible-character stripping, NFKC + homoglyph
folding). Since the canary value is rendered directly into the model's own
context (`assembly.ts`'s `renderInertSpan`), a model instructed by injected
content to reproduce "internal markers" with a cosmetic alteration — a
zero-width character spliced in, a Cyrillic/Greek look-alike substituted for
a Latin letter — could reflect an evasive form the weak normalizer would
never match.

**Fix:** both sides of the comparison (the payload being scanned and each
stored canary) now go through `normalizeMatchText`. Regression fixtures cover
zero-width space, ZWJ/ZWNJ, a Cyrillic homoglyph substitution, and an
NFKC-foldable fullwidth character, each spliced into an actual generated
canary token and confirmed detected. Combining-diacritical-mark ("zalgo")
obfuscation is a related but distinct gap — `normalizeMatchText` folds NFKC
and a fixed homoglyph table but does not strip Unicode category Mn — tracked
separately as #46 and *not* asserted as fixed here.

## #41 — JSON-in-string provenance blind spot (+ #44 unbounded recursion)

`attribution.ts`'s `extractStrings` (feeding `argumentProvenanceMatch` and
`contentSensitivityCheck`) walked tool-call arguments without parsing JSON
embedded in string leaves or double-escaped payloads, unlike `egress.ts`'s
`collectLeafStrings`, which did both plus a depth guard. A sensitive value
nested inside a JSON-stringified sub-field was checked as one opaque blob
that essentially never matches a span verbatim (the span holds the plain
value, not the surrounding JSON syntax), so it silently failed to attribute
to its true origin — defeating the "arguments originate only from inert
spans" gate for every sensitive tool *other than* the two (`send_email`,
`http_post`) with bespoke egress destination handling.

**Fix:** extracted one shared, guarded traversal (`src/traversal.ts`),
handling objects/arrays, JSON-in-string (including double serialization),
cycles, and a fixed depth budget (`TRAVERSAL_MAX_DEPTH = 8`) — matching the
issue's explicit requirements. Both `attribution.ts` and `egress.ts` now
import it; `src/testing/tool-oracle.ts` deliberately keeps its own
independent copy (its design rules forbid importing Aegis code, to keep the
differential benchmark non-circular). Regression coverage: a value nested one
level inside JSON-in-string, a value nested behind *double*-escaped JSON, and
an integration-level test proving `decideAttribution` now blocks a
`delete_file` call whose target is smuggled this way even when a sibling
field satisfies whole-call intent (mirroring the #39 PoC's shape, but for the
provenance gate rather than egress authorization).

While unifying the traversal, corrected an incidental divergence: the old
`egress.ts` traversal used a "seen anywhere" `Set` for cycle avoidance, which
silently dropped a DAG's second, non-circular reference to a shared
sub-object (a legitimate value referenced from two argument fields would lose
its second occurrence). The shared traversal uses an ancestor-path `Set`
(unwound on the way back up), matching `attribution.ts`'s existing correct
semantics — verified with a dedicated regression.

**#44 (unbounded recursion), closed as a side effect:** the shared
traversal's depth guard means a deeply nested (but acyclic) `tool_args`
payload no longer risks a stack-overflow crash inside
`collectLeafStrings`/`hasCircularReference`. One residual crash site
remained even after that: `decideAttribution` calls plain
`JSON.stringify(args)` for args-canary detection, which is not depth-guarded
and recurses natively — found via a test with 50,000 levels of nesting that
still threw a `RangeError` after the traversal fix. `decideAttribution` now
catches any `RangeError` raised by code it calls and converts it to the same
typed, fail-closed `AegisAttributionError` the existing circular-reference
guard already throws, rather than letting an uncaught crash reach the
caller.
